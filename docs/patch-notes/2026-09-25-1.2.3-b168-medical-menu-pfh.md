# ACM Extended 1.2.3 B168

## Root cause: medical-menu renderer ownership

B168 fixes the renderer lifecycle itself rather than adding another treatment-specific recovery.

The key observation was that Direct Pressure could make otherwise inert buttons work again without recreating the
medical menu. Direct Pressure explicitly invokes one `updateActions` pass. Tourniquet treatment also recovered the
menu because it closes/recreates the medical display. That points at the process which continuously drives
`updateActions`, not at Narc Box, CPR, Semi-Fowler or medication callbacks individually.

ACE stores the medical-menu renderer PFH in one global `ace_medical_gui_menuPFH` handle. ACME's overridden
`onMenuOpen` retained ACE's stock rule:

> if a menu PFH already exists, reuse it and do not create another one.

That is unsafe when a medical display is rapidly replaced. CPR, BVM, Head Tilt-Chin Lift, Semi-Fowler and other
multi-stage procedures can close/reopen the interface on adjacent frames. A new display can become current while the
old display's delayed `onUnload` is still pending. The old unload then removes the global PFH, even though that
handle is now the renderer for the new/current display.

The result is exactly the reported state:

- the medical menu remains visible;
- its controls may retain the last labels/conditions/handlers which happened to be painted;
- actions which require current row rebinding can appear to do nothing;
- Direct Pressure makes everything work again because it explicitly calls `updateActions`;
- closing/reopening the menu makes everything work again because a fresh display gets another renderer pass.

There was a second concrete lifecycle defect: ACME already had
`addons/gui/overrides/fnc_onMenuClose.sqf`, but **CfgFunctions did not register it**, so runtime was still using
ACE's stock global-unqualified close function.

## B168 renderer lifecycle

B168 makes the renderer PFH display-generation owned.

On each medical-menu open:

1. the new display receives a monotonically increasing renderer generation;
2. any previous renderer PFH is retired;
3. one PFH is created for this exact display + generation;
4. every tick verifies that the display and generation are still current before calling the normal
   `ace_medical_gui_fnc_menuPFH`.

On close:

1. the display releases only its own provider/menu-pose ownership;
2. a stale display unload returns immediately if a newer display has already replaced it;
3. only the current display may clear `pendingReopen`, remove the current renderer PFH, or clear
   `ace_medical_gui_menuDisplay`;
4. PFH removal is additionally checked against the handle stored on that exact display.

This prevents an old CPR/BVM/minigame menu unload from killing the renderer of a newly reopened menu.

## Scope

B168 does **not** add Narc Box, CPR, medication, tourniquet or Direct Pressure exceptions to the action renderer.
`fnc_updateActions.sqf` is intentionally unchanged from B167/B165.

The fix is at the shared renderer-driver lifecycle used by every medical-menu action.

B167's explicit Head Tilt-Chin Lift/manual Semi-Fowler menu-return work is retained, but B168 does not depend on
those actions for renderer recovery.
